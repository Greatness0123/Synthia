# Coordinator → `src/` Refactoring: Revised Analysis

**Update:** The original rationale for the split architecture has been invalidated. The coordinator was designed as a separate process because it was expected to run against Kaggle notebooks or Ollama (local inference servers requiring dedicated GPU processes, custom Python environments, and independent process lifecycle management). The project has since moved to cloud APIs (Gemini, OpenRouter, NVIDIA NIM, Groq, custom OpenAI-compatible endpoints). The coordinator is now **simply an HTTP orchestration layer** — it builds prompts, calls cloud APIs, parses responses, and writes to Supabase. There is no local inference happening. The process separation is unnecessary overhead, not architectural wisdom.

## What Changes With Cloud APIs vs. Local Inference

| Aspect | Kaggle/Ollama (Original Plan) | Cloud APIs (Current Reality) |
|--------|------------------------------|------------------------------|
| Process needs | Dedicated GPU process, Python venv, model loading time | Simple HTTP POST — any Node.js process can do this |
| Scaling concern | Coordinator needed independent scaling (GPU server separate from frontend) | Cloud APIs handle scaling — coordinator is just a thin proxy |
| Crash isolation | Kaggle notebooks crash/restart unpredictably — needed separate process | Cloud APIs are stable — coordinator failures are rare |
| Dependency weight | Heavy: `@xenova/transformers`, `onnxruntime-node`, Python subprocess management | Light: `node-fetch` is the only real requirement |
| Separation benefit | Real: coordinator could run on GPU box while frontend ran on dev machine | None: coordinator is just another Node module that makes HTTP calls |

## Legacy Code That Should Be Removed

### 1. `coordinator/src/providers/kaggleProvider.ts`
This 95-line provider is a dead code path. It POSTs the raw InferPayload to a local Kaggle server and parses the stream. With cloud APIs as the primary path, this adapter serves no purpose. If Kaggle support is ever needed again, it can be re-added — but today it's maintenance burden with zero usage.

### 2. `coordinator/src/embeddingEngine.ts` + `coordinator/models/Xenova/` (~80MB)
The local all-MiniLM-L6-v2 embedding model is used by `memoryManager.ts` to generate vector embeddings for memory similarity search before writing to Supabase. Two questions:
- **Is local embedding still needed?** If memory search quality is acceptable without it, this is 80MB of disk + `@xenova/transformers` dependency that could be eliminated. Supabase itself supports `pgvector` — embeddings could be generated by a Supabase Edge Function or a cloud embedding API.
- **Could embeddings be generated by the same cloud LLM?** Gemini and OpenAI-compatible APIs all offer embedding endpoints. This would shift the embedding workload to the cloud, aligning with the overall architectural direction.

If local embeddings are kept, the model needs to move from `coordinator/models/` to the project root.

### 3. `set_endpoint` WebSocket Message
The `server.ts` handler has a `set_endpoint` case that sets `kaggleEndpoint` and calls `agent.setEndpoint(data.url)`. This was the Kaggle-specific configuration path. With cloud APIs, the `set_provider` message (which carries `type`, `endpoint`, `apiKey`, `model`) is the correct way to configure inference. The `set_endpoint` message type and `kaggleEndpoint` variable can be removed.

### 4. `coordinator/src/reconnectionManager.ts` — Kaggle-Specific Logic
The reconnection manager has a special `verifyEndpointReachable()` method that pings `/health` and an `if (this.config.providerType === 'kaggle')` branch. With Kaggle gone, this simplifies to generic retry logic.

## What the Refactored Architecture Looks Like

After merging, the coordinator code becomes part of the same source tree but **still runs as a separate Node.js process** (because it's a server, and the frontend is a browser app — they can't share a runtime). The difference is organizational:

```
Before (Two separate projects):
  /coordinator/         ← Own package.json, own tsconfig.json, own node_modules
  /src/                 ← Own package.json, own tsconfig.json, own node_modules
  Shared types → manually synced, 4 duplicated files

After (One project, two build targets):
  /src/
    /coordinator/       ← Same source tree, compiled by dedicated tsconfig
    /shared/types/      ← Single source of truth for all interfaces
    /components/        ← Frontend (unchanged)
    /store/             ← Frontend (unchanged)
    /world/             ← Frontend (unchanged)
  package.json          ← All deps in one place
  tsconfig.coordinator.json  ← Server build config
  tsconfig.json         ← Project references (app + node + coordinator)
```

## Quick Wins Available Before Full Move

These can be done **today** without moving any coordinator files:

1. **Delete KaggleProvider** — ~95 lines removed, zero impact on working functionality
2. **Delete `set_endpoint` handler** from `server.ts` — ~5 lines cleanup
3. **Remove `kaggleEndpoint` variable** from `server.ts` and `agentLoop.ts`
4. **Simplify `reconnectionManager.ts`** — remove Kaggle-specific health check branch
5. **Extract shared types** to `src/shared/types/` — eliminate 4 duplicated files

These 5 steps reduce the coordinator by ~200 lines, remove one dead code path, and eliminate the type duplication problem — all without changing the directory structure or runtime at all.

## The Core Question: Is the WebSocket Server Still Necessary?

Given that the coordinator's job is now:
1. Receive world state via WebSocket
2. Call a cloud LLM API
3. Parse the response
4. Write to Supabase
5. Stream results back via WebSocket

...the architectural question becomes: **Could the browser call the LLM API directly?**

**Answer: No, for good reasons that survive the refactoring:**

- **API keys must never be exposed to the browser.** The coordinator keeps Gemini/OpenRouter API keys server-side.
- **Supabase service role key** (used for memory writes) has admin privileges and must never reach the client.
- **Prompt building is complex** (300+ line system prompts with joint axis maps, perception summaries, tactile context). This belongs server-side.
- **Memory vector similarity search** queries Supabase with embeddings — this logic is server-side regardless of where embeddings are generated.
- **Dataset export** uses FFmpeg and filesystem access — impossible in browser.

So the coordinator (the *function*, not the *directory*) is still necessary. The question is only about code organization.

If local embeddings are moved to the cloud:

| Dependency | Still Needed? | Why |
|-----------|---------------|-----|

| `@supabase/supabase-js` | ✅ Yes | Memory/session/skill storage |
| `dotenv` | ✅ Yes | Environment config |
| `uuid` | ✅ Yes | Memory IDs |
| `zod` | ✅ Yes | Payload validation |

| `ws` | ✅ Yes | WebSocket (used by fastify/websocket) |

## TypeScript Version Conflict — Real But Solvable

The coordinator was written for TS 5.6.2 and uses:
- `module: "NodeNext"` / `moduleResolution: "NodeNext"` — for Node.js ESM
- `import fetch from 'node-fetch'` — CommonJS interop

The frontend was upgraded to TS 6.0.2 and uses:
- `module: "esnext"` / `moduleResolution: "bundler"` — for Vite
- React JSX, DOM types

**Solution:** The coordinator gets its own `tsconfig.coordinator.json` that extends a base config. TS 6 is backward-compatible for most patterns — the coordinator code uses standard TypeScript (classes, interfaces, async/await) with no exotic features. The risk of TS 6 breakage is low for this codebase.

The coordinator's tsconfig needs:
```json
{
  "compilerOptions": {
    "target": "ES2022",
    "module": "NodeNext",
    "moduleResolution": "NodeNext",
    "outDir": "./dist/coordinator",
    "rootDir": "./src",
    "strict": true,
    "esModuleInterop": true,
    "skipLibCheck": true
  },
  "include": ["src/coordinator/**/*", "src/shared/**/*"]
}
```

This goes into the root project references:
```json
// tsconfig.json
{
  "files": [],
  "references": [
    { "path": "./tsconfig.app.json" },
    { "path": "./tsconfig.node.json" },
    { "path": "./tsconfig.coordinator.json" }  // NEW
  ]
}
```

## npm Script Changes

Before:
```json
"scripts": {
  "dev": "vite",
  "coordinator": "cd coordinator && npm run dev",
  "build": "tsc -b && vite build"
}
```

After:
```json
"scripts": {
  "dev": "vite",
  "coordinator": "tsx src/coordinator/server.ts",
  "coordinator:dev": "tsx watch src/coordinator/server.ts",
  "build": "tsc -b && vite build",
  "build:coordinator": "tsc -p tsconfig.coordinator.json",
  "start:coordinator": "node dist/coordinator/server.js"
}
```

Note: `tsx` replaces `ts-node` for running TypeScript directly. `tsx` is faster, supports ESM better, and is already a common dev dependency. Or `ts-node` can be kept.

## Communication Protocol — Unchanged

The frontend still connects to `ws://localhost:3001/ws`. The WebSocket message types (`world_state`, `action`, `thought_token`, `outcome`, `set_provider`, `set_supabase`, `inject_thought`, `export_request`, etc.) are all unchanged. The coordinator still runs on port 3001. The refactoring is purely file-level — zero protocol changes.

## Risks Assessment (Revised)

| Risk | Severity | Mitigation |
|------|----------|------------|
| Build complexity (two compilation targets) | Medium | Separate tsconfig files, clear npm scripts, documentation |
| TS version conflict | Low | Coordinator code is standard TS; TS 6 is backward-compatible for these patterns |
| Dependency bloat in root node_modules | Low | Vite tree-shakes; coordinator deps are ~200MB (acceptable for a dev project) |
| Dev accidentally imports coordinator code in React | Low | Separate tsconfig excludes coordinator from app compilation; Vite's bundler resolution won't find Node.js modules |
| Coordinator breaks after move | Medium | Thorough end-to-end testing before deleting old directory |
| Supabase/local model path changes | Low | Update `cache_dir` in embeddingEngine, `process.cwd()` paths in server.ts |

## Recommendation (Revised)

**Phase 1 — Immediate Cleanup (1 hour):**
1. Delete `kaggleProvider.ts` (dead code)
2. Remove `set_endpoint` handler and `kaggleEndpoint` variable from `server.ts` and `agentLoop.ts`
3. Simplify `reconnectionManager.ts` (remove Kaggle health check)
4. Extract 4 shared type files to `src/shared/types/`
5. Update imports in both `src/` and `coordinator/src/` to use shared types
6. Delete old duplicate type files

This phase has **zero risk** — it removes dead code and fixes the type duplication problem. Everything still works exactly as before.

**Phase 2 — Dependency Audit (2 hours):**
1. Determine if local embeddings are still desired, or if a cloud embedding API should be used
2. If cloud: remove `@xenova/transformers`, delete `models/Xenova/`, replace embedding calls with API
3. If local: plan to move `models/` to project root
4. Test coordinator on TypeScript 6

**Phase 3 — Source Code Move (1 day):**
1. Create `tsconfig.coordinator.json` at root
2. Move coordinator source files to `src/coordinator/`
3. Merge `package.json` dependencies
4. Update npm scripts
5. Move `coordinator/programs/` to root `programs/` (or `src/coordinator/programs/`)
6. Move `coordinator/models/` to root if keeping local embeddings
7. Update all internal import paths
8. End-to-end testing (frontend ↔ coordinator ↔ cloud API ↔ Supabase)
9. Delete old `coordinator/` directory

**Phase 4 — Optional: Vite Plugin Integration (future)**
As a future enhancement, the coordinator could be started automatically as part of `vite dev` via a Vite plugin. This would give a single-command `npm run dev` that starts both the frontend dev server and the coordinator. This is a nice-to-have, not required for the refactoring.

## Answer to "Will the Software Still Work Fine Without the Separation?"

**Yes.** The coordinator's responsibilities (build prompt → call cloud API → parse response → write to Supabase) are standard Node.js tasks. There is nothing about these tasks that requires a separate process boundary. The WebSocket server (port 3001) is the only runtime interface — as long as it starts and accepts connections, the frontend doesn't care what directory the source code lives in or whether it shares a `package.json`.

The separation was a premature architectural decision based on a deployment scenario (local GPU inference) that never materialized. Removing it simplifies the codebase with no functional degradation. The communication protocol (WebSocket on port 3001) and the process boundary (separate Node.js process for the server) remain intact — only the file organization changes.
