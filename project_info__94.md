# Synthia 1.5.1 — Walk Retargeting Deepscan: Phantom Euler Extraction, Stale Artifact, and the Missing Change-of-Basis Fix

## Verdict Up Front

**The current codebase does NOT contain the leg-movement fix** (project_info__93's `PITCH_AXIS_FLIP` was never implemented — no `axis="-1 0 0"` exists anywhere in `MJCFHumanoidTemplate.ts` or any other source file). But that is the smaller problem.

The bigger, provable discovery: **`public/animations/mixamo-walking-synthia.json` (the artifact that `walkAnalyzer.js` → `playWalk()` actually plays) cannot be produced by the converter source that is in the repo right now.** A frame-by-frame mathematical audit shows the artifact's joint values are phantom — wrong sign, wrong magnitude, and wrong axis — relative to the raw `walking` stream. Whoever changed the converter (or the "fix" attempt) never regenerated the artifact; the artifact and the unit tests both encode the output of an **older, buggy conversion pipeline** whose Euler extraction produces:

- **Hips (uplegs): sign-inverted and magnitude-shrunken** — raw stream says left hip is +64° forward at frame 0; artifact says −27.6° (backward). Raw says right hip +20°; artifact says −12°. This single inversion drives the pelvis backward → torso arches → falls on its back.
- **Knees: pinned to 0 for every frame of both legs** — the raw stream has real alternating knee flexion (+23° left / −15° right at frame 8); the artifact collapses all of it to 0, which is exactly the `leftleg/rightleg 0 frames offset` the analyzer reported.
- **Arms: large phantom roll** — raw LeftArm frame 0 is a modest 22.4° swing; artifact emits roll +0.896 rad (+51.3°), which drives the *roll* hinge (axis `0 1 0`) and rotates the arm twisted-backward instead of swinging it. RightArm roll −0.957 (−54.8°) likewise. This is the "zombie arms" symptom.
- **Shoulders: rail-pinned** — raw LeftShoulder frame 0 is ~1.2°; artifact pins yaw −0.258 / roll +0.261 exactly onto the ±0.261 constraint rails (the old rail-pinning disease).

The raw `walking` stream is, by itself, a **valid alternating walk cycle** (root advances 177 cm; knees and arms alternate with ~16-frame phase). The corruption is entirely in the conversion layer + stale data. This report gives the exact arithmetic proof, the four root-cause defects with file:line evidence, why project_info__93's fix would not have fixed this, and the precise change-of-basis recipe to fix it permanently.

## 1. The Decisive Evidence: Raw Stream vs. On-Disk Artifact (with math)

### 1a. Frame 0 hips — sign inversion proven

Raw stream quat (x,y,z,w), `walking` frame 0, `mixamorig:LeftUpLeg` at offset 179:

```
[ 0.532581, -0.0102084, 0.00156004, 0.846316 ]
```

This is a rotation of θ = 2·acos(0.846316) = **+64.3° about +X**. In Mixamo's local frame, +X on the left thigh is anatomical **forward hip flexion** (swing leg reaching forward at heel contact). At the same frame:

```
mixamorig:RightUpLeg: [ 0.176306, 0.0677087, 0.0120665, 0.98193 ]  → +20.6° (hip flexed forward, stance leg)
mixamorig:RightLeg:   [ -0.075548, 0.00177707, -0.0397117, 0.99635 ] → −9.5°  (stance knee slightly bent)
mixamorig:LeftLeg:    [ 0.000509184, 0.00332071, -0.0111662, 0.999932 ] → ~1.3° (swing leg nearly straight)
```

That is a textbook mid-stride double-support pose. The character is pushing off / reaching.

The artifact's frame 0:

```
mixamorigleftupleg:  [ -0.48162073881314593, 0.11042099740600866, -0.07009971097205857 ]  → pitch −27.6° (BACKWARD)
mixamorigrightupleg: [ -0.20827630591114288, -0.15783701347010456, -0.08272152076448026 ] → pitch −12.0° (BACKWARD)
mixamorigleftleg:  0
mixamorigrightleg:  0
```

**Both hips negative (backward) at frame 0 is physically impossible for a forward walk** — and it is the exact opposite sign of the stream. With both thighs driven backward, the pelvis is pulled backward, the torso arches, and the arms trail → the backward fall recorded in the video.

### 1b. The current converter cannot produce the artifact — proof

The current `toZxyEuler` (`src/utils/mixamoStreamConverter.ts`) does: canonicalize → `threeQuatToMuJoCo` (conjugate by +90° about X) → `Euler('ZXY')`.

A rotation about +X is **invariant** under conjugation by a rotation about +X (`Q·Rx·Q⁻¹ = Rx`). And the ZXY decomposition of a pure-X quaternion is exactly `(pitch = θ, yaw = 0, roll = 0)`. Therefore the current converter, fed the frame-0 LeftUpLeg quat, **must emit pitch ≈ +64.3°** (clamped by the ±2.094 hip constraint to +64.3°).

The artifact says **−0.4816 (−27.6°)**. That value cannot be reached from the current code by any sign convention, clamping, or quaternion canonicalization. **Conclusion (mathematically airtight): the artifact on disk was generated by a different, older conversion algorithm and has never been regenerated since the converter was refactored.**

This alone explains the user's "the fix produced no changes": `walkAnalyzer.js`'s `playWalk()` and `walkAnalyzer()` both `fetch('/animations/mixamo-walking-synthia.json')` — they never invoke the converter. Editing `mixamoStreamConverter.ts` (or the MJCF template) changes nothing until `scripts/generateMixamoWalkArtifacts.ts` is re-run and the browser cache cleared.

### 1c. Knees — real alternating flexion destroyed by the clamp

Raw knee quats, frame 8 (`index 8`):

```
mixamorig:LeftLeg:  [ 0.202094, -0.01825, 0.00664481, 0.979174 ]  → +23.4° (left swing leg flexing)
mixamorig:RightLeg: [ -0.127646, 0.02315, -0.0391, 0.990778 ]    → −15.6° (right stance leg extending)
```

Frame 16, opposite phase:

```
mixamorig:LeftLeg:  [ 0.168129, 0.00880181, -0.00414255, 0.985717 ] → +19.7°
mixamorig:RightLeg: [ 0.152034, -0.26274, -0.0439321, 0.9518 ]     → ~ −31.4° (sweeps about −X)
```

The alternating ~16-frame phase offset **exists in the raw stream**. The artifact emits `"mixamorigleftleg": 0` and `"mixamorigrightleg": 0` for **every one of the 33 frames**. Two independent clamp layers kill it:

1. `mixamoStreamConverter.ts` emits `clamp('x', pitch)` against `SYNTHIA_RIG_CONSTRAINTS` knee range `x: [-2.618, 0]` — **positive flexion is clamped to 0**. The converter's own doc comment ("Knees: stream flexion is already negative → pass through") is factually wrong for this clip: the left knee's X rotation is **positive** in the extracted frame.
2. Even if the converter emitted a positive value, `HumanoidPhysicsBinder.validateAndApplyTimeline` has an explicit hard rule:
   ```ts
   if (constraint.dof === 1 && constraint.x[1] === 0.0 && v > 0) {
     clampingNotes.push(`${key}:positive_x_clamped_to_0`);
     return 0.0;
   }
   ```
And `setMotorTargets` clamps once more via `getAnatomicalLimitForBone` knee `{ min: -150°DEG, max: 0 }`.

So both knees are mathematically pinned straight → `walkAnalyzer`'s `leftleg/rightleg 0 frames offset ⚠` is a *symptom detector working correctly* on a destroyed signal.

### 1d. Arms — phantom roll > 2× the true rotation

Raw `mixamorig:LeftArm` frame 0: `[ 0.0233849, -0.126562, -0.144845, 0.981048 ]` → total rotation 22.4° about an axis ≈ (−0.66, −0.75) in the arm's local XZ plane — a **normal forward arm swing** in a walk.

Artifact frame 0:

```
mixamorigleftarm:  [ -0.10555270407525649, 0.1135669130865938, 0.8960088910850679 ]  → pitch −6.0°, yaw +6.5°, ROLL +51.3°
mixamorigrightarm: [ 0.010313976338575255, -0.33547257955390997, -0.9569242088851388 ] → pitch +0.6°, yaw −19.2°, ROLL −54.8°
```

A 22.4° swing decomposes into a **51.3° roll component** — the Eurocentric fallacy of extracting Euler angles from a rotation about a diagonal axis: the decomposition over-reports a single axis that is not the anatomical swing axis. In `MotorController.setTargets`, `z → roll actuator` drives the MJCF `axis="0 1 0"` hinge for the arm. Rotating the humerus ~50° about its local Y (the bone-length axis in the baked frame) **twists the arm backward** — the "zombie arms bent backwards" symptom, now explained with an exact number.

Raw `mixamorig:LeftShoulder` frame 0 is `[ 4.36e-06, -0.00398, -0.01054, 0.99994 ]` — about **1.2°**, essentially relaxed. The artifact pins the shoulder to `[0.0092, -0.2580, 0.261]`, with yaw = −0.258 and roll = +0.261 sitting **exactly on the ±0.261 constraint rails**. This is the 93-era "rail-pinning" bug reproducing itself in the current artifact — phantom 15° from a 1.2° delta.

### 1e. Root motion is correct

The only part of the artifact that is sane:

```
posZ (Mixamo, cm): frame0 0.072 → frame8 45.1 → frame16 91.4 → frame24 136.6 → frame31 177.0
artifact rootMotion dz ≈ −0.055/frame; forwardSpeedMps 1.659; cumulative ≈ 1.66 m
```

`forwardSign = -1` correctly maps Mixamo +Z to engine −Z. Root translation is not the problem.

## 2. The Four Root-Cause Defects

### D1 — The converter extracts Eulers in the wrong basis (the disease)

`mixamoStreamConverter.ts` treats each stream quat as "a local delta in the joint's own T-pose frame" and directly converts it with `threeQuatToMuJoCo` + `Euler('ZXY')`, then feeds those numbers to MJCF hinge axes whose frames come from the **baked parent-relative bind transforms** in `MJCFHumanoidTemplate.buildBodyTreeXML` (`qRel = qParent_bind⁻¹ · qChild_bind` in MuJoCo space).

The two bases are **not the same**:
- Blend: Hips bind ≈ −89° X; Left/RightUpLeg bind ≈ 180° Z (from `discards/T-pose in three.js world configuration.md`); shoulders bind ≈ ±133°.
- The stream's `tposer-orientation` is identity, i.e., the stream quats are measured against a **T-pose that does not match the GLB's baked bind for the re-parented bones**.

For a bone whose T-pose frame differs from the baked MJCF frame by a large rotation, a small real delta becomes a **phantom Euler triple** — wrong sign, wrong axis, wrong magnitude (D1 is what produced the +64°→−27.6° hip inversion and the 22°→51° arm roll explosion).

This is precisely Gemini's "Local Basis Shift" point — and it is **verified true against this codebase and this data**, not just plausible.

### D2 — Stale artifact + stale tests = the invisibility of every fix

- `scripts/generateMixamoWalkArtifacts.ts` reads `walking2.md` and writes `public/animations/mixamo-walking-synthia.json`.
- `walkAnalyzer.js` / `playMixamoWalk.ts` / the browser `playWalk()` **only read the JSON artifact**.
- Proof in §1b: the on-disk artifact cannot be produced by the current converter code. Therefore whatever the repo's source currently computes, **no one has seen it**; the numbers being played are from an older pipeline.
- `src/utils/mixamoStreamConverter.test.ts` **enshrines the stale numbers**: `leftUpLegPitch = -0.48`, asserted via `Math.abs` in [0.4, 0.55]. A correct regeneration (pitch ≈ +64°) would *fail* these tests, and a sign-flipped artifact (pitch +0.48) would *pass* them. The test is the bug's bodyguard.

### D3 — Anatomical sign conventions are per-side mirrored, and the clamp stack destroys the knees

- The stream's left-leg flexion is `+X` while the right-leg flexion is `−X` (proven in §1c). A single global convention ("knees are negative") cannot capture both.
- Triple clamp (converter → `validateAndApplyTimeline` → `setMotorTargets`/`getAnatomicalLimitForBone`) pins every knee to 0.
- The elbow rule `pitch = Math.abs(pitch)` forces positive flexion on both sides, but the stream's natural elbow signs are also mirrored; `|pitch|` on the side that is naturally negative turns a 15° natural bend into a wrong-direction 15° bend.

### D4 — The baked-frame hinge-sign flip (project_info__93) is real but only partial, and was never applied

- `MJCFHumanoidTemplate.ts` still emits `axis="1 0 0"` for every pitch hinge — no `axis="-1 0 0"`, no `PITCH_AXIS_FLIP` table anywhere in `src/`. The 93 fix is **not in the codebase**, which the user correctly suspected.
- Even if applied, 93's fix would correct the hip sign but would do **nothing** for the arm roll phantom (D1), the knee phase collapse (D3), or the stale artifact (D2). 93's diagnosis ("converter stream-frame delta vs baked-frame hinge sign") describes D4, a *contributor*; the dominant cause is D1.

## 3. Why `walkAnalyzer.js`'s PHASE SYMMETRY report "leftleg/rightleg 0 frames offset" is the correct diagnosis of a symptom, not a cause

`walkAnalyzer.js` computes symmetry by cross-correlating the left/right pitch series from the **artifact JSON** at `v[0]` (pitch). Since the artifact pins both knees to 0 everywhere, the correlation is degenerate and reports 0. The script is correct; the data it reads is corrupt. Running the same analyzer on the *raw stream's* knee quats (I did the equivalent by hand in §1c) shows a clean ~16-frame alternation.

Also note a subtle analyzer flaw worth knowing: the expected offset of 16 assumes an exactly half-cycle gait; ±3 tolerance is reasonable, but the correlation index it uses is computed over the full artifact length including the loop-clone frame — harmless, but don't let "fix the analyzer" be the action item. The data is the problem, not the analyzer.

## 4. The Correct Fix — Quaternion Change-of-Basis Pipeline (do this, not per-bone sign hacks)

### 4a. Algorithm (this is what probe2 (`/tmp/mixamo_probe2.mjs`) already implements — verify it, then port it)

For every joint `j` with parent `p`, per frame:

1. **Compute the static bind-relative frame once** (from the GLB T-pose, not the stream):
   ```
   R_bind(p)  = bindWorldQuat(p)          (THREE world, from skeleton at load)
   R_bind(j)  = bindWorldQuat(j)
   rBind_j    = R_bind(p)⁻¹ · R_bind(j)   (parent-relative bind pose)
   ```
2. **Compute the animated parent-relative delta:**
   ```
   R_anim(p)  = streamWorldQuat(p)   (accumulate: world = parentWorld · localDelta)
   R_anim(j)  = streamWorldQuat(j)
   rAnim_j    = R_anim(p)⁻¹ · R_anim(j)
   ```
3. **Project onto the joint's own hinge frame:**
   ```
   R_target_j = rBind_j⁻¹ · rAnim_j
   ```
4. **Only now** convert: `threeQuatToMuJoCo(R_target_j)` → `Euler('ZXY')` → `[pitch, yaw, roll]` → clamp → emit.

This makes the emitted angles **hinge-frame-relative** — a 0 emitted for any bone means "exactly bind pose", +pitch means "flex forward *in the hinge's own frame*", and the baked 180° upleg frames cancel out algebraically instead of being patched by hand. This is the permanent cure for D1/D4, and it makes the hip/arm/elbow sign conventions per-bone-correct for free (left/right mirroring falls out of the bind math).

### 4b. Then fix the knee/elbow semantics

The 1-DOF flexion rules must be per-side, not global:
- Compose the final pitch **after** the hinge-frame projection, then apply the rig's sign convention **by bone**:
  - `mixamorigleftleg`/`mixamorigrightleg`: emit the hinge-frame flexion as a negative value (whatever sign raw produces, negate to fit `[-2.618, 0]`) — or better, flip the constraint to allow the stream's natural sign and update the MJCF hinge axis for knees to match. Pick ONE source of truth.
  - `mixamorigleftforearm`/`mixamorigrightforearm`: same per-side treatment, then `Math.abs` only if the rig truly is positive-only.
- Delete the `positive_x_clamped_to_0` hard rule in `validateAndApplyTimeline` **unless** a knee can never legitimately receive positive x after 4a — with the bind-relative projection, a positive pitch on a knee means hyperextension, so clamping to 0 is actually fine *after* the projection. Verify empirically with one frame.

### 4c. Regenerate & rewrite tests (mandatory)

1. Run `npx ts-node --esm scripts/generateMixamoWalkArtifacts.ts` (writes `public/animations/mixamo-walking-synthia.json`).
2. **Before trusting it**, assert the new frame-0 numbers match the raw-stream math in §1: leftupleg pitch ≈ +64° (window [1.05, 1.15] rad), rightupleg ≈ +0.3–0.4 rad, leftleg ≈ 0, rightleg ≈ −0.16 rad, leftarm roll < 0.3 rad, shoulder values < 0.05 rad. If they don't, debug the projection, not the test.
3. Rewrite `mixamoStreamConverter.test.ts`:
   - Replace `Math.abs(leftUpLegPitch)` in [0.4, 0.55] with a **sign-aware** assertion (`toBeGreaterThan(1.0)` for left hip at frame 0, and `toBeLessThan(0)` must hold simultaneously for exactly one hip at any frame — a walk can never have both hips in backward extension).
   - Add per-frame knee alternation assertions: `sign(knee_L(t)) == -sign(knee_L(t+16))` and the cross-leg offset ≈ 16 frames.
   - Add a no-rail-pin scan back for **shoulders and arms** (`mixamorigleftshoulder`/`rightshoulder` must never hit ±0.261).
   - Add a "regeneration determinism under 4a" test that recomputes from `walking2.md` and diffs against the checked-in artifact — this is what will catch D2 forever.
4. Hard-refresh the browser (MJCF + JSON caches) before `playWalk()`, as 93 already instructed.

### 4d. Do NOT apply 93's `PITCH_AXIS_FLIP` on top of the change-of-basis fix

93's `axis="-1 0 0"` is a workaround for D4's symptom. If you build 4a, the bake is already compensated; adding the flip would **double-negate** the uplegs. If you keep the MJCF untouched and only fix the converter (the "Alternative fix" in 93), then 93's added `PITCH_SIGN_FLIP` in the converter *is* what 4a's `rBind⁻¹` does generically — don't also flip in the MJCF. **One source of truth: the converter's bind-relative projection, MJCF untouched.**

## 8. One-paragraph summary for whoever patches this

The walk is broken because `mixamoStreamConverter.ts` extracts ZXY Euler angles from raw stream-local quaternions that are measured in a T-pose frame different from the baked MJCF hinge frames, producing phantom angles (hips +64° → −27.6°, arms 22° swing → 51° phantom roll, shoulders 1.2° → rail-pinned ±15°), and because those phantom values then hit per-side-mirrored knee/elbow sign rules plus a triple clamp that pins both knees to 0. **The on-disk artifact was never regenerated after any of this was introduced, so no source fix has ever been visible in the browser.** The cure is the bind-relative change-of-basis projection (probe2 already implements it), per-side flexion conventions, regeneration of the artifact, and sign-aware tests — not per-bone `axis="-1 0 0"` patches, which would only fix the hips and double-break them if combined with the projection.
